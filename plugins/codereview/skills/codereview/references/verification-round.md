# Verification round — the orchestrator's side

Read this when a re-review range (`base=` from an earlier round) has prose files: Phase A step 9 printed `PROSE_SCOPE` with a `DOCS` or `DOC_ONLY` file. It decides which files go to a verifier, launches the verifiers and closes the earlier round's findings in Phase C. The verifier's own contract is `verify-agent.md`; only the verifier reads it.

## When it runs

All of these hold, or the re-review runs as a full round (SKILL.md, Phases B and C as written) and the report's `Round` line names the one that failed, `ran in full: {reason}` (report-template.md):

- `base=` names the head an earlier round reviewed, and the review is not in `worktree` mode (configuration.md): an uncommitted fix gives the script no range.
- The `base=` commit is an ancestor of the head: `git merge-base --is-ancestor {MERGE_BASE} HEAD` (`head=<sha>` in place of `HEAD`) exits 0. After a fixup or a rebase the script's three-dot range would cover the whole branch, so the re-review runs as a full round.
- The session holds that round's open findings (number, `file:line`, kind, claim), in the conversation or in a file it names; without that list, the re-review runs as a full round. The list stays with the session: no prompt carries it.
- The user passed no `verify=off`.
- `prose_units.py` exited 0. A non-zero exit means no scope, never "no prose files".
- An agent can be launched. The verifier is always an agent, never inline, whatever the file count: when no agent can be launched (runtime-routing.md, the inline fallback), there is no verification round.

## Which files

A file goes to a verifier only when it is on Phase A's FILES list (a path-scoped review leaves the rest of the range out), `PROSE_SCOPE` gives it `kind` `DOCS` or `DOC_ONLY` and at least one unit, and Phase A did not classify it EXCLUDED or CONFIG: Phase A's classification wins over the script's `kind`. Every other file on the FILES list follows today's flow: a deleted file (status `D`, whose entry has `units: []`), a `kind: CODE` file, any file with `units: []`, and an EXCLUDED or CONFIG one.

The script errs toward `CODE`. Only line comments (`//`, `#`, `--`) count, and each of these makes a file `CODE`: a changed block-comment line; a renamed, re-moded, new or deleted code file; `.yml`/`.yaml`/`.toml`, `requirements*.txt` and `CMakeLists.txt`; a prose file whose changes land in no unit; a changed `//` line holding `*/`, a `--` line that opens a Lua block comment (`--[[`, `--[==[`) or holds a long-bracket close (`]]`, `]==]`) anywhere, and in C and C++ a `//` line ending in `\`; a changed comment line a tool reads — one that starts `#!`, `# -*-`, `/// <reference`, `---@`, `//# `, `//@ `, `//line `, `//extern `, `//export ` or Go's `//word:x` (`//go:build`, `//nolint:errcheck`), one whose text starts with a `+word` marker (`// +build`, `// +kubebuilder:…`, `-- +goose`) or with `@ts-`, `@flow`, `@jsx`, `eslint-`, `prettier-ignore`, `biome-ignore`, `istanbul ignore`, `c8 ignore`, `type:`, `mypy:`, `pyright:`, `pylint:`, `fmt:`, `isort:`, `pragma:`, `nosec`, `frozen_string_literal:`, `rubocop:`, `typed:`, `nolint`, `NOLINT`, `clang-format`, `shellcheck`, `swift-tools-version`, `swiftlint:` or `<auto-generated`, and one holding `noqa`, `coding:` or `coding=` anywhere, in any case; and a comment block a tool reads whole, around a changed line: a Go example's `Output:` block in a `_test.go`, the block right above `import "C"` (a cgo preamble), and a Rust `///` or `//!` block with a fence (a doctest).

Declared limit: the script misses a `#`, `//` or `--` line inside a multi-line string or heredoc, and any line a tool reads that the list above lacks; only the verifier's backstop covers them. A verifier reports such a line as `[HIGH] not prose` (verify-agent.md): its file then takes today's flow in this round, as after a failed relaunch (*Launch*), and counts as `kind: CODE` for the sweep rule below. That finding is not graded; the flow's own findings are. A file the session already knows holds such a line takes that flow from the start.

The sweep (Phase B2) is skipped only in a verification round where no file of the range left outside the verifiers is `kind: CODE` (the script's) or a file Phase A classified CONFIG. A full round, `worktree` mode included, runs it as written.

## Launch

One verifier takes at most 400 unit lines (`unit_lines`) and 12 files. Above that, split by file across more verifiers in the same batch; a single file over 400 unit lines splits by unit ranges, each verifier given only its own ranges on its `Units:` line. `model: REVIEW_MODEL` on every call. Emit only the launch prompt below, placeholders filled — nothing added, nothing removed; exception: a refused `Read` under `{SKILL_DIR}` (runtime-routing.md, *Contrato ilegível*). Under `head=<sha>`, write that sha for `HEAD` in the diff and the `Range:` line.

```
Agent(model: REVIEW_MODEL, prompt: "
Start with ONE batch of parallel tool calls: Read {SKILL_DIR}/references/verify-agent.md and run
`git -P diff {MERGE_BASE}...HEAD -- {PROSE_FILES}`. Then follow verify-agent.md exactly.

- Repository: {REPO}
- Range: {MERGE_BASE}...HEAD
- Units: {one line per unit: path:start-end (changed: n, n)}
- Identifiers: {per file, from PROSE_SCOPE}
- Evidence: {path or none, per file}
- Skill dir: {SKILL_DIR}
- Hard rules: {CLAUDE.md prohibitions, verbatim, or none}
")
```

A verifier whose message does not end in `END_OF_VERIFICATION`, or whose `Units read:` is below the number of units it was given, counts as missing its sentinel: it is relaunched once, with the same files, base and head. When it still falls short, its files take the full flow in this round (a per-file agent each, and the sweep by the rule above), and their open findings stay open until that flow answers.

## Closing the earlier round's findings (Phase C, after step 1)

For each open finding of the earlier round, read the range's diff over its lines. One whose lines the diff did not touch, on any file, in the range or outside it, stays open and counts in the grade, unless a written verdict dismissed it. One the diff touched closes by its file's path:

- On a file a verifier held and did not report `not prose` on: it closes only when its unit was read by a verifier whose message ended in `END_OF_VERIFICATION` and whose `Units read:` covered every unit it was given, the diff touched that unit, and the verifier gave no `behavior` there.
- On any other file (`kind: CODE`; a `DOCS` or `DOC_ONLY` file Phase A classified EXCLUDED or CONFIG; a deleted file; a `not prose` file; a verifier's files after its relaunch failed): it closes or stays open by today's rule, on what that flow reports; it is never dropped.

Each finding that stays open is carried over: a row of the report's Findings Table, counted in the grade (report-template.md). From a verifier's *Outside scope* list, a `behavior` on a line the branch wrote counts like any finding. The rest (a `form`, or a line older than the branch) does not count and is not dropped: list it in the report's *Outside scope (tracker)* bucket, with the total of the verifiers' `Cut:` lines.

Declared limit: older drift outside the edited units is not sought; it is the first round's job (configuration.md, *Re-review rounds*, first item).
